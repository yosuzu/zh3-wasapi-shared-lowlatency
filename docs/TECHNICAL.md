# ZH3 的 WASAPI 共享模式怎样跑到 256 帧

**中文** | [English](TECHNICAL.en.md)

ZH3 Control 1.0.0

项目的起点是让 osu!lazer 在使用 Fosi Audio ZH3 时有机会缩短音频输出延迟，同时保留 Windows 共享混音，让其他应用也能发声。先要回答一个可以直接测量的问题：在 44.1 kHz 下，原厂驱动只向共享模式提供 441 帧，能否让应用请求 256 帧，并确认引擎确实按这个周期运行？

一台 ZH3 使用 Fosi 驱动 6.16.0.15392 时，将可变下限设为 **3.5 ms**，Windows 公布的范围变为 **155–441 帧，步进 1 帧**。独立测试客户端开流前读到 **441 帧（10 ms）**，请求 256 帧并启动后读到 **256 帧（5.805 ms）**，停止前仍为 256 帧。另一项试验选择 **0.5 ms 下限**后，REAL v0.2.0 在 44.1 kHz 下将 **23 samples（0.521542 ms）** 标为当前值。两次观察的工具与条件见下文。其他使用普通 WASAPI 共享模式、能够显式请求短周期的应用，也可以用同一组 API 检验自己的播放流。osu!lazer 本身的周期、长时间有声播放和按键到出声的延迟仍待实测。

## 先把三个量分开

| 量 | 怎样取得 | 256 帧样本说明了什么 |
| --- | --- | --- |
| 引擎周期 | `IAudioClient3::GetCurrentSharedModeEnginePeriod` 返回当前共享音频引擎每轮处理的帧数和格式。立体声的一帧含左右各一个采样。 | 256 ÷ 44,100 ≈ 5.805 ms。相同格式下原厂为 10 ms，共享引擎可以更频繁地处理音频。 |
| 客户端缓冲容量 | 已初始化的客户端调用 `IAudioClient::GetBufferSize`，取得端点缓冲最多容纳的帧数。实际排队量可另读 `GetCurrentPadding`。 | 容量为 562 帧。同一条流可以每 256 帧调度一次，并持有更大的缓冲。 |
| 端到端延迟 | 把输入或应用触发时刻与实际输出对时测量，例如同时记录触发信号和 ZH3 的模拟输出。 | 游戏处理、应用缓冲、引擎调度、USB 传输和设备内部处理均会影响结果。本次静音试验没有对应测量值。 |

仅调整可变下限时，原厂的 10 ms 仍是 Windows 向应用公布的默认值。运行期间真正用多少，取决于客户端请求和引擎当时的状态。需要确认某个游戏是否用上短周期时，应在它实际播放期间读对应端点的当前周期，同时记录其他共享客户端的活动。[微软的共享周期查询说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getcurrentsharedmodeengineperiod) · [缓冲容量说明](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getbuffersize)

## 从三个容易误判的结果开始

- 同一台 ZH3 换用 Windows 自带 USB Audio 2.0 驱动后，44.1 kHz 基线为默认 441、步进 1、最小 309、最大 441。一次包周期覆盖使驱动接口发布的最小间隔从 7 ms 降至 6 ms，但设备重新枚举、Windows 重启后，普通共享模式的最小值仍为 309 帧（约 7.01 ms）。单读驱动发布的属性，会把这一轮误判为成功。
- Fosi 5.68 和 6.16.0.15392 的原厂基线都是四项各 441 帧。早期在已有的 KS（Kernel Streaming，Windows 驱动层音频接口）上写入 7 ms，再重新枚举，四项仍各为 441 帧。后续试验改为追踪驱动为新命名播放档发布的接口。
- 早先见到的一条 256 帧记录来自独占播放。独占播放绕过普通共享混音，无法据此确定共享引擎的下限。为检验同一个数字，后续固定使用普通共享模式、同一混音格式和确切的活动播放端点。

## 四组对照

四轮试验在同一台 ZH3、同一版 Fosi 6.16.0.15392 上独立进行。均使用 44.1 kHz、双声道、32 位浮点的共享混音格式，客户端类别为 `Other`，关闭硬件卸载（offload），不请求 RAW。每轮写入前和撤销完成后，同格式查询的四项均为 **441 / 441 / 441 / 441**。下表的步进是 Windows 公布的基本周期，单位为帧。表中的 OEM 周期指设备厂商可提供给音频引擎的周期值。

| 试验输入 | 默认 | 步进 | 最小 | 最大 | 独立共享流的运行结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 固定 8 ms，写 OEM 周期 | 353 | 353 | 353 | 353 | 请求 353 帧，启动后和停止前均读回 353。 |
| 下限 8 ms，OEM 留空 | 441 | 1 | 353 | 441 | 分别请求 353、400 帧，两条流首尾各自读回请求值。 |
| 下限 3.5 ms，OEM 留空 | 441 | 1 | 155 | 441 | 分别请求 155、156、256 帧，三条流首尾各自读回请求值。 |
| 下限 3 ms，同时写 5 ms OEM | 221 | 221 | 221 | 221 | 请求 221 帧成功。133、134 均越出所公布范围，探针在调用初始化之前退出。 |

8 ms 下限时，256 帧低于最小值 353。把下限降到 3.5 ms 后，向上取整得到 `ceil(0.0035 × 44100) = 155` 帧，256 才落入这次证实可用的范围。155 与 156 两个相邻请求各自成功，也实际检验了最小值附近的 1 帧步进。256 帧样本在约 2.005 秒内记录到 346 次事件，音频时钟向前推进，流正常停止。它证明共享引擎能按应用的请求运行，听感和持续负载下的稳定性需要另测。

组合试验回答了另一个开发问题：如果同时写入默认周期和下限，能否得到 5 ms 默认、3 ms 最小？接口层的两项输入都已读回，端点也收到了 5 ms OEM 属性，引擎却只公布固定的 221 帧。一种与数据相符的解释是，此处的非零 OEM 输入让引擎沿用了固定周期计算。现场没有跟踪引擎运行的分支。就这台设备而言，有实测依据的是固定值或可变下限两条路线，尚无证据支持任意独立设定默认值、下限和步进。

## 在 REAL 中验证 0.5 ms 下限

在 ZH3 Control 选取可变模式最低可提交的 **0.5 ms**，再用 **REAL v0.2.0** 查看默认播放设备。截图显示采样率为 **44100 Hz**，`Buffer size (min)` 一行是 **23 samples (0.521542 ms) [current]**，`max` 与 `default` 均为 **441 samples (10 ms)**。因此这个现场同时观察到更小的当前值和保留的 10 ms 默认值。[REAL 实测截图](images/real-44100hz.png) · [REAL 上游项目](https://github.com/miniant-git/REAL)

按前述可变下限的换算，`0.0005 × 44100 = 22.05`，向上取整为 **23 帧**，对应 `23 / 44100 × 1000 ≈ 0.521542 ms`。这解释了界面上的请求刻度与 REAL 读数之间的微小差距。REAL 在这张截图中标记的是默认播放设备，未显示具体型号或基本步进。其窗口使用 `Buffer size` 和 `samples` 这两个标签，不能据此把 23 当作独立测得的客户端缓冲容量。3.5 ms 试验另有指向特定活动端点的初始化、运行首尾读回及音频时钟记录。0.5 ms 的截图支持此次 REAL 的现场读数，仍缺该档长时有声稳定性和模拟端到端延迟测量。

## 两条路线如何落到 Windows 端点

**共同起点是当前的设备路径。** 正式程序从唯一在场的 ZH3 物理 USB 实例出发，核对其直接 KS 子设备、两层容器标识、驱动版本以及服务名 `FosiAudioUsbAudio` 和 `FosiAudioUsbAudioks`。再从活动播放端点的连接器找到对应的接口引用与播放流。Windows 默认输出格式从 `PKEY_AudioEngine_DeviceFormat` 读取，共享引擎混音格式则从 `GetMixFormat` 读取。两者可能有不同的有效位深。切换格式后，活动引用可能随播放档位变化，程序会重新定位相应接口。[设备、接口和活动流定位](../app/src/probe/pnp.rs) · [端点、格式和周期读取](../app/src/probe/audio.rs)

**两条路线都借用 Fosi 的命名播放档。** 驱动从物理 USB 实例的 `Device Parameters\Config` 读取配置。正式实现先核对当前播放流与双声道格式，为新档和条目分配新名字，检查 AUDIO、RENDER 两种接口的在场和历史注册记录，避免与旧引用重名。档内 `SoundDeviceProfiles\<档名>\<条目名>` 的 `Type` 为 DWORD 0，`Loc_00` 和 `Loc_01` 的 `ChannelIndex` 分别为 DWORD 0 和 1。命名档的接口引用由当前基础引用、下划线和条目名组成，例如 `pcm_out_02_c_00_<条目名>`。按所选路线准备好属性后，最后在当前 `StreamFormatOut_<编号>` 将 `CurrentSoundDeviceProfile` 选为新档名。源配置使用注册表事务，提交前后均核对值。重新枚举后，再找出驱动实际启用的具名接口。这些键、名称和发布行为来自 Fosi 驱动。[配置构造与提交](../app/src/profile.rs) · [注册表读取与事务](../app/src/profile/registry.rs)

| | 固定周期 | 可变下限 |
| --- | --- | --- |
| 交给驱动的内容 | 在命名条目 `ks\EP\0` 写 `PKEY_AudioEngine_OEMPeriod`（PID 6），保持 `PKEY_AudioEngine_PeriodUseDefault`（PID 7）缺失。 | PID 6、7 都保持缺失。选档前，用 `SetupDiCreateDeviceInterfaceW` 在目标 KS 子设备上预注册尚未启用的 `KSCATEGORY_AUDIO` 具名引用，再用 `SetupDiSetDeviceInterfacePropertyW` 设置二进制属性 `DEVPKEY_KsAudio_PacketSize_Constraints2`。 |
| 怎么核对 | 8 ms 样本中，AUDIO、RENDER 接口均读到 OEM 包装，活动 MMDevice 端点读到包装内的 8 字节。固定档跳过 AUDIO 预注册。 | 设置完成后，SetupAPI 和 Configuration Manager 分别读回新 AUDIO 接口的包长。重新枚举后，活动 AUDIO 复用了准备好的引用和包长。驱动生成的同名 RENDER 可以没有这项包长。 |
| 引擎给客户端的结果 | 8 ms 样本只有 353 帧可选，用默认周期也会选到这一数值。 | 两个实测档均保留默认 441 帧，并允许显式请求从新下限起、以 1 帧递增的周期。 |

固定档的 8 ms 样本在源配置中是 16 字节的 `REG_BINARY`。前 4 字节为小端 `VT_BLOB`（65），接着 4 字节写载荷长度 8，末尾 8 字节为小端整数 80000，单位为 100 ns。可变档写的是另一种结构。两组实测均为 40 字节，前四个小端 DWORD 依次为最小间隔（100 ns）、包字节对齐掩码、最大包字节数、处理模式约束数。只有第一个字段非零，8 ms 为 80000，3.5 ms 为 35000，余下 24 字节也为零。当前项目的 1 帧步进来自 Windows 对这两组声明给出的读数。其他对齐设置能否得到指定的步进，仍需实测。[Rust 接口属性与双读实现](../app/src/profile/interface.rs) · [微软 WDK 的约束结构定义](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-_ksaudio_packetsize_constraints2)

## 正式工具如何判断生效和恢复

四组开流数据来自开发阶段的配置原型和独立 C# 播放探针。0.1.5 的 Rust 程序负责确认设备、配置、重启和只读探测。界面的探针不会替目标应用开流或设置游戏参数。0.1.5 在真实窗口读到过 44.1 kHz、当前周期 441 帧。早期 0.1.2 在 Windows 选用 24 位输出时，分别于 48 kHz 和 384 kHz 读到原厂 480 和 3840 帧。这些是格式识别与原厂周期读数。适配验证还缺第二台实体电脑及这些格式下的切档与实际播放。[只读探针](../app/src/probe.rs) · [窗口与设备操作控制](../app/src/controller.rs)

- **保存与生效分开验收。** 写入自定义周期仅支持 6.16.0.15392 的双声道播放流，确认时重新核对设备与格式。程序用 Windows 的 `pnputil /restart-device` 定向重启已核对的物理 USB 实例。之后要重新定位活动端点，核对活动引用、属性与当前格式公布的四项周期。两种模式互斥，切换路线前需完成原厂恢复验收。滑条每格 0.5 ms，可提交 0.5–10 ms。固定档低于 5 ms 可能回落到 10 ms，低于 3 ms 也可能无声，可变档低于 3 ms 同样提示风险。滑条刻度和引擎的帧步进各有单位，实测范围见上表。[生效核对逻辑](../app/src/profile.rs) · [操作提示](../app/ui/index.html)
- **返回码提示去哪里查，端点读数决定是否成功。** 3.5 ms 试验的启用和撤销均通过定向软件重启完成，两个 8 ms 档使用物理拔插。组合试验撤销时返回 3010（需要重启），事件 225 指出 `audiodg.exe` 阻止设备移除。稍后重试返回 50（不支持此请求），活动端点仍为 221 帧，直到物理拔插才恢复四项各 441。驱动保留的停用 RENDER 上仍有一份 5 ms 副本。另一次在 0.1.2 保存 1.0 ms 下限后，Fosi 控制面板阻止重启，随后恢复了原厂设置。这次没有取得 1.0 ms 已进入活动端点的证据。[重启诊断](../app/src/profile/restart.rs)
- **后备重连另行确认。** 当前程序会提示退出仍在系统托盘运行的 Fosi 控制面板，并检查这台 ZH3 的待重启标志。普通重启受阻、失败或超时未生效时，只有本次待处理操作和当前 USB 拓扑（父集线器、端口及设备身份）仍可核对，才提供单独确认的一次端口重连。1.0.0 实机验收中，官方面板打开时普通重启暂缓。退出面板后，分别通过普通重试使可变档生效、通过目标 USB 端口重连使原厂恢复生效。重启或拔插会中断播放，操作前应先降低音量。[USB 端口定位与重连](../app/src/usb_port.rs)
- **撤销实验与整机恢复有不同目标。** 历史试验按写前状态和本次回执撤销，逐轮验收活动端点回到原厂。正式程序的“恢复原厂”会重新确认物理设备，枚举它已登记的全部播放档，取消已有自定义选档，包括当时未活动的档。在已知原厂属性的驱动版本上，还会清除原厂播放基础接口上的周期覆盖。程序保持当前采样率或位深，跳过未登记的档，保留录音配置、驱动默认选档和无法核实归属的闲置档案。成功条件包括选档及基础接口复核，并读到活动端点的原厂状态。端点暂不可用时显示待验收。全档恢复流程已有代码和离线检查，1.0.0 已在真机从固定和可变两种配置恢复到原厂，结束时全设备命名选档数为零。[全播放档恢复](../app/src/profile/factory.rs) · [跨重启的恢复状态](../app/src/profile/factory_state.rs)
- **回执按设备和播放流关联。** 读取窗口不会创建操作日志。写配置时，程序将状态放在 EXE 同级的 `ZH3-Data`，按设备和播放流轮换文件，并在 HKLM（本机注册表）保存对应校验信息。这样能区分两个位深对应的播放流，也能在中断后核对哪些配置归本程序所有。[回执与归属核验](../app/src/profile/store.rs)

### 1.0.0 正式 EXE 的真机对照

在 44.1 kHz 双声道共享混音下，通过 1.0.0 窗口保存和恢复，每到一个稳定状态，就用 0.1.5 从同一目录重新探测，核对设备、活动端点、格式、模式和公布的四项周期。以下播放验证使用提交静音数据的独立客户端，记录初始化后的当前周期和停止前的读数。

| 界面操作 | 默认 / 步进 / 最小 / 最大（帧） | 独立读回 |
| --- | --- | --- |
| 保存可变下限 3.5 ms | 441 / 1 / 155 / 441 | 请求 256 帧，首尾均为 256。关闭再打开窗口后仍识别同一配置。 |
| 保存固定周期 8 ms | 353 / 353 / 353 / 353 | 请求 353 帧，首尾均为 353。 |
| 恢复原厂并等待活动端点 | 441 / 441 / 441 / 441 | 当前 441 帧，全设备自定义选档数为零。 |

两种模式均核对过“保存 → 取消”，设备继续按原厂配置工作，随后可用保留的草稿再次确认。兼容性试验中，先用 0.1.5 保存 0.5 ms 可变下限，关闭旧窗口，再在同一目录启动 1.0.0。新版识别旧回执并读到 23 帧最小值，静音客户端请求 23 帧后首尾均读回 23 帧。最终通过新版恢复了原厂。周期观测与上文 REAL 的读数可以互相对照。实际游戏端到端延迟、长时间高负载音质以及第二台实体电脑仍需另行测量。

## 怎样在另一款音频应用或另一块声卡上验证

1. **先记录同格式基线。** 锁定目标活动播放端点，记录 Windows 与驱动版本、端点方向、共享混音格式和 Windows 默认输出格式。在该端点激活 `IAudioClient3`，用 `SetClientProperties` 明确客户端类别、offload 和 RAW 选项。向 `GetSharedModeEnginePeriod` 传入同一份混音格式，保留默认、基本步进、最小、最大四项，再用 `GetCurrentSharedModeEnginePeriod` 记录开流前的帧数和格式。[可选周期查询](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod)
2. **用请求方自己的流验证。** 若 `Min ≤ N ≤ Max`、基本步进为正且 `N % Fundamental == 0`，用 `InitializeSharedAudioStream` 请求 N 帧。记录初始化返回值、`GetBufferSize`、启动后及停止前的当前格式和帧数，并验证音频时钟推进。共享引擎也会受其他客户端影响，应记录哪些客户端正在工作。启动失败、收到不同周期或格式发生变化，都应按实际结果保留。只测真实应用时，至少把它开始和停止播放的时间同端点采样对齐。[共享流初始化](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)
3. **确认自己的驱动提供什么。** 可以先用驱动正式提供的设置做一次对照，只改一个变量，保持端点、格式、客户端参数可比。分别记录驱动接口声明、Windows 公布的范围和应用运行中的周期。切档若使端点重新枚举，需从设备重新找到活动端点。ZH3 上使用的命名档、服务名、接口引用、OEM 包装和可恢复的原厂属性，都需要针对各自厂商另行确认。
4. **让结论能由别人重查。** 每档保留修改前、修改后、恢复后的同格式四项读数，以及所请求的帧数、运行首尾读回、缓冲容量和时长。分享时用同一组匿名代号关联设备与端点即可。若要说明对游戏体验的收益，还需在同一输入和音频链路上测量调整前后的端到端延迟。若要声称适合日常播放，还需在目标负载下做长时有声测试并记录掉音。
