# How the ZH3 reached 256 frames in WASAPI shared mode

[中文](TECHNICAL.md) | **English**

ZH3 Control 1.0.0

This project started with a question about osu!lazer and the Fosi Audio ZH3. Could the game output audio with less delay while still using the Windows shared mixer, so other applications could play sound too? The first step was to measure something concrete. At 44.1 kHz the stock driver offered shared-mode clients a single period of 441 frames. Could a client request 256 frames and verify that the engine actually ran at that period?

On one ZH3 with Fosi driver 6.16.0.15392, setting the minimum period to **3.5 ms** made Windows report a range of **155–441 frames in steps of 1 frame**. An independent test client read **441 frames (10 ms)** before opening its stream. It requested 256 frames, read **256 frames (5.805 ms)** after starting playback, and read 256 again just before stopping. In a separate test with a **0.5 ms minimum**, REAL v0.2.0 marked **23 samples (0.521542 ms)** as the current value at 44.1 kHz. The sections below give the conditions and tools for each measurement. Other applications that use ordinary WASAPI shared mode and can explicitly request a shorter period can check their streams with the same APIs. The period osu!lazer actually uses, stability during sustained audible playback, and the time from a keypress to sound are still unmeasured.

## Three different measurements

| Quantity | How to measure it | What the 256-frame test showed |
| --- | --- | --- |
| Engine period | `IAudioClient3::GetCurrentSharedModeEnginePeriod` returns the format and the number of frames the shared audio engine processes per cycle. A stereo frame contains one sample for each channel. | 256 ÷ 44,100 ≈ 5.805 ms. The stock period for the same format was 10 ms, so the shared engine could process audio more frequently. |
| Client buffer capacity | After initialization, `IAudioClient::GetBufferSize` returns the maximum number of frames the endpoint buffer can hold. `GetCurrentPadding` reports how many frames are queued at the time of the call. | The buffer held up to 562 frames. The stream could run on a 256-frame schedule with a larger buffer. |
| End-to-end latency | Measure the input or application trigger and the actual output against a common clock, for example by recording a trigger signal and the ZH3's analog output together. | Game processing, application buffering, engine scheduling, USB transport, and processing inside the device all contribute. The silent-stream test yielded no end-to-end measurement. |

Changing only the minimum leaves the stock 10 ms period as the default Windows advertises to applications. The period in use depends on what the client requests and the state of the engine when it makes the request. To check a particular game, read the current period on its playback endpoint while the game is producing audio, and record which other shared-mode clients are active. [Microsoft on reading the current shared-mode period](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getcurrentsharedmodeengineperiod) · [Microsoft on buffer capacity](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient-getbuffersize)

## Three early results that were easy to misread

- With the Windows USB Audio 2.0 driver on the same ZH3, the 44.1 kHz baseline was a default of 441 frames, a step of 1, a minimum of 309, and a maximum of 441. A packet interval override lowered the minimum advertised by the driver interface from 7 ms to 6 ms. Even after the device was re-enumerated and Windows restarted, ordinary shared mode still reported a minimum of 309 frames (about 7.01 ms). Reading only the driver property would have given a false impression of success.
- Fosi drivers 5.68 and 6.16.0.15392 both had stock readings of 441 frames for all four values. An early attempt wrote 7 ms on an existing Kernel Streaming (KS) interface, the Windows driver-level audio interface. All four readings remained at 441 after re-enumeration. Later tests tracked the interface the driver published for a newly named playback profile.
- An earlier 256-frame observation came from exclusive-mode playback. Exclusive mode bypasses ordinary shared mixing, so that observation could not establish a lower limit for the shared engine. The later tests checked the same number using ordinary shared mode, the same mix format, and the specific active playback endpoint.

## Four controlled tests

Four independent tests used the same ZH3 and Fosi driver 6.16.0.15392. All used a 44.1 kHz stereo, 32-bit floating-point shared mix format, the `Other` client category, hardware offload disabled, and no RAW request. Before each change and after its rollback, querying the same format returned **441 / 441 / 441 / 441**. The step in the table is the fundamental period Windows reported, in frames. The OEM period is a period value the device manufacturer can supply to the audio engine.

| Configuration tested | Default | Step | Minimum | Maximum | Independent shared-stream result |
| --- | ---: | ---: | ---: | ---: | --- |
| Fixed 8 ms, OEM period set | 353 | 353 | 353 | 353 | Requested 353 frames. Read 353 after starting and just before stopping. |
| 8 ms minimum, OEM period absent | 441 | 1 | 353 | 441 | Requested 353 and 400 frames in separate streams. Each returned the requested period at the start and end. |
| 3.5 ms minimum, OEM period absent | 441 | 1 | 155 | 441 | Requested 155, 156, and 256 frames in separate streams. Each returned its requested period at both readings. |
| 3 ms minimum with a 5 ms OEM period | 221 | 221 | 221 | 221 | A request for 221 frames succeeded. Both 133 and 134 fell outside the advertised range, so the probe exited before calling the initialization API for either value. |

With an 8 ms minimum, 256 frames fell below the 353-frame lower bound. With a 3.5 ms minimum, rounding up gives `ceil(0.0035 × 44100) = 155` frames, bringing 256 into the verified range. Successful requests for both 155 and 156 also tested the 1-frame step next to the minimum. The 256-frame stream recorded 346 events over about 2.005 seconds. Its audio clock advanced and the stream stopped normally. This demonstrates that the shared engine could run at the requested period. Sound quality and stability under sustained load require separate measurements.

Could supplying both a default and a minimum give a 5 ms default with a 3 ms minimum? Both inputs were read back at the interface, and the endpoint received the 5 ms OEM property. The engine advertised a single period of 221 frames. One explanation consistent with the data is that the nonzero OEM value led the engine to use a fixed-period calculation. The test did not trace which code path the engine took. The measurements support two configurations on this device, a fixed period and an adjustable minimum. They do not establish that the default, minimum, and step can all be chosen independently.

## Checking the 0.5 ms minimum with REAL

With the minimum set to **0.5 ms**, the lowest value ZH3 Control accepts in variable mode, **REAL v0.2.0** was used to inspect the default playback device. The screenshot shows **44100 Hz**. The `Buffer size (min)` row reads **23 samples (0.521542 ms) [current]**. Both `max` and `default` read **441 samples (10 ms)**. The lower current value and the retained 10 ms default were visible in the same observation. [REAL measurement screenshot](images/real-44100hz.png) · [REAL upstream project](https://github.com/miniant-git/REAL)

The conversion used above gives `0.0005 × 44100 = 22.05`. Rounding up gives **23 frames**, or `23 / 44100 × 1000 ≈ 0.521542 ms`. This explains the small difference between the slider setting and the value in REAL. The screenshot identifies the default playback device without showing its model or the fundamental step. REAL uses the labels `Buffer size` and `samples`. Those labels alone do not establish an independently measured client buffer capacity of 23 frames. The 3.5 ms test separately recorded stream initialization on a specific active endpoint, period readings at the start and end, and audio clock progress. The screenshot documents what REAL observed on this occasion. Long-running audible playback and analog end-to-end latency at the 0.5 ms setting still need testing.

## How the two configurations reach a Windows endpoint

**Both start by identifying the current device.** The released tool starts from the single connected ZH3 physical USB instance, checks its direct KS child, the container IDs at both levels, the driver version, and the service names `FosiAudioUsbAudio` and `FosiAudioUsbAudioks`. It then follows the active playback endpoint's connector to identify the corresponding interface reference and playback stream. It reads the Windows default output format from `PKEY_AudioEngine_DeviceFormat` and the shared engine's mix format from `GetMixFormat`. The two formats can have different valid bit depths. Switching output formats can activate a different playback profile and interface reference, so the tool locates the interface again. [Device, interface, and active stream lookup](../app/src/probe/pnp.rs) · [Reading the endpoint, formats, and periods](../app/src/probe/audio.rs)

**Both configurations use a Fosi named playback profile.** The driver reads its configuration from `Device Parameters\Config` on the physical USB instance. The tool verifies the current playback stream and stereo format, assigns fresh names to the profile and entry, and checks current and historical AUDIO and RENDER interface registrations to avoid reusing an existing reference. In `SoundDeviceProfiles\<profile name>\<entry name>`, `Type` is DWORD 0. The `ChannelIndex` values for `Loc_00` and `Loc_01` are DWORD 0 and 1 respectively. The named profile's interface reference consists of the current base reference, an underscore, and the entry name, for example `pcm_out_02_c_00_<entry name>`. Once the properties for the chosen configuration are ready, the tool selects the new profile by setting `CurrentSoundDeviceProfile` under the current `StreamFormatOut_<number>`. It writes the source configuration in a registry transaction and checks the values before and after the commit. After re-enumeration it locates the named interface the driver actually activated. These keys, names, and interface publication details are specific to the Fosi driver. [Constructing and committing the configuration](../app/src/profile.rs) · [Registry reads and transactions](../app/src/profile/registry.rs)

| | Fixed period | Adjustable minimum |
| --- | --- | --- |
| Driver inputs | Write `PKEY_AudioEngine_OEMPeriod` (PID 6) under `ks\EP\0` in the named entry. Leave `PKEY_AudioEngine_PeriodUseDefault` (PID 7) absent. | Leave PIDs 6 and 7 absent. Before selecting the profile, call `SetupDiCreateDeviceInterfaceW` on the target KS child to register the inactive named `KSCATEGORY_AUDIO` reference, then call `SetupDiSetDeviceInterfacePropertyW` to set the binary `DEVPKEY_KsAudio_PacketSize_Constraints2` property. |
| Verification | In the 8 ms test, the AUDIO and RENDER interfaces both exposed the wrapped OEM value. The active MMDevice endpoint exposed the 8-byte payload. The fixed-period configuration skips AUDIO preregistration. | SetupAPI and Configuration Manager each read back the packet-size constraint on the new AUDIO interface. After re-enumeration, the active AUDIO interface reused the prepared reference and constraint. The RENDER interface the driver creates with the same name can lack this property. |
| What clients see | The 8 ms test offered only 353 frames. Asking for the default also selects that period. | In both measured configurations the default stayed at 441 frames. Clients could explicitly request periods from the new minimum upward in steps of 1 frame. |

In the fixed 8 ms test, the source configuration stored a 16-byte `REG_BINARY` value. The first 4 bytes held little-endian `VT_BLOB` (65), the next 4 held a payload length of 8, and the final 8 held the little-endian integer 80000, in 100 ns units. The adjustable-minimum configuration wrote a different structure, 40 bytes in both tests. Its first four little-endian DWORDs were the minimum interval (100 ns units), packet byte alignment mask, maximum packet size in bytes, and number of processing mode constraints. Only the first field was nonzero, with 80000 for 8 ms and 35000 for 3.5 ms. The remaining 24 bytes were also zero. The 1-frame step was observed in what Windows reported for these two sets of constraints. Whether other alignment settings can produce a specified step still needs testing. [Rust interface property and dual readback implementation](../app/src/profile/interface.rs) · [Microsoft WDK definition of the constraints structure](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ksmedia/ns-ksmedia-_ksaudio_packetsize_constraints2)

## How ZH3 Control verifies changes and restores factory settings

The four controlled stream tests above used a development configuration tool and an independent C# playback probe. The 0.1.5 Rust application handled device identification, configuration, restarts, and read-only probing. Its UI probe does not open a stream on behalf of the target application or change game settings. The 0.1.5 window displayed a current period of 441 frames at 44.1 kHz on the device. Earlier, with 24-bit output selected in Windows, 0.1.2 read stock periods of 480 frames at 48 kHz and 3840 frames at 384 kHz. These observations verify format detection and factory-period readback. Profile switching and playback at those formats, and testing on a second physical computer, remain outstanding. [Read-only probe](../app/src/probe.rs) · [Window and device operations](../app/src/controller.rs)

- **Saving a configuration and verifying that it took effect are separate steps.** Custom period writes are supported only for stereo playback streams on 6.16.0.15392. On confirmation, the tool rechecks the device and format. It uses Windows `pnputil /restart-device` to restart the verified physical USB instance, locates the active endpoint again, and checks the active interface reference, properties, and four advertised periods for the current format. The two modes are mutually exclusive. Switching between them requires a verified factory restore first. The slider accepts 0.5–10 ms in steps of 0.5 ms. Fixed periods below 5 ms may fall back to 10 ms. Fixed periods below 3 ms may also produce silence, and variable mode also shows a warning below 3 ms. Slider increments are in milliseconds. The measured engine steps in the table above are in frames. [Verification logic](../app/src/profile.rs) · [Operation prompts](../app/ui/index.html)
- **Restart codes help diagnose failures. Endpoint readings determine success.** A targeted software restart applied and rolled back the 3.5 ms test. Both 8 ms tests used physical unplugging and reconnection. During rollback of the combined test, the restart returned 3010 (restart required), and event 225 identified `audiodg.exe` as blocking device removal. A later retry returned 50 (request not supported). The active endpoint stayed at 221 frames until a physical reconnection restored all four readings to 441. An inactive RENDER interface retained by the driver still held a copy of the 5 ms value. In a separate test, the Fosi control panel blocked the restart after 0.1.2 saved a 1.0 ms minimum. Factory settings were subsequently restored. There was no evidence that the 1.0 ms setting had reached the active endpoint. [Restart diagnostics](../app/src/profile/restart.rs)
- **The fallback USB reconnection requires a separate confirmation.** The current tool prompts the user to exit the Fosi control panel if it is still running in the system tray and checks whether this ZH3 is marked as requiring a restart. If the normal restart is blocked, fails, or times out before the change takes effect, the tool offers one separately confirmed port reconnection only if it can still verify both the pending operation and the current USB topology (parent hub, port, and device identity). In the 1.0.0 hardware test, opening the official control panel caused the tool to defer the normal restart. After the panel was closed, a normal retry applied the variable profile, and a targeted USB port reconnection subsequently applied the factory restore. Restarting or reconnecting the device interrupts playback. Lower the volume first. [USB port lookup and reconnection](../app/src/usb_port.rs)
- **Rolling back a test and restoring the device have different scopes.** Each historical test used the state recorded before the write and that operation's receipt to undo its own changes. The active endpoint was checked for factory settings after every rollback. In the released tool, the factory restore rechecks the physical device, enumerates all its registered playback profiles, and clears custom profile selections, including selections for currently inactive formats. On driver versions with known factory properties, it also clears period overrides on the factory playback base interfaces. The tool preserves the current sample rate and bit depth, skips unregistered profiles, and preserves recording configurations, driver default selections, and unused profiles whose ownership it cannot verify. To report success, it checks the profile selections and base interfaces, then reads the factory state from the active endpoint. If the endpoint is temporarily unavailable, verification remains pending. The all-profile restore has been implemented and tested offline. In hardware tests, 1.0.0 restored factory settings from both fixed and variable configurations, with zero named profiles selected across the device at the end. [Restoring all playback profiles](../app/src/profile/factory.rs) · [Restore state across restarts](../app/src/profile/factory_state.rs)
- **Operation receipts identify the device and playback stream.** Opening the window to inspect the device creates no operation log. When writing a configuration, the tool rotates state files by device and playback stream in `ZH3-Data` beside the EXE and stores matching verification data in the local machine registry (HKLM). This distinguishes the playback streams used by two different bit depths and lets the tool verify which configuration changes it owns after an interruption. [Receipts and ownership checks](../app/src/profile/store.rs)

### Hardware cross-check with the 1.0.0 release executable

The 1.0.0 window was used to save and restore settings with a 44.1 kHz stereo shared mix. Each time the device reached a stable state, 0.1.5 was run from the same directory to cross-check the device, active endpoint, format, mode, and all four advertised periods. For the playback checks, an independent client submitted silent data and recorded the current period after initialization and again just before stopping.

| Operation in the window | Default / step / minimum / maximum (frames) | Independent reading |
| --- | --- | --- |
| Save a 3.5 ms variable minimum | 441 / 1 / 155 / 441 | Requested 256 frames and read 256 at both ends of the run. Closing and reopening the window still identified the same configuration. |
| Save a fixed 8 ms period | 353 / 353 / 353 / 353 | Requested 353 frames and read 353 at both ends. |
| Restore factory settings and wait for the active endpoint | 441 / 441 / 441 / 441 | Current period 441 frames, with zero custom profiles selected across the device. |

The **Save → Cancel** sequence was tested in both modes. The device continued to use factory settings and the draft selection remained available for later confirmation. In a compatibility test, 0.1.5 first saved a 0.5 ms variable minimum. Its window was closed and 1.0.0 was launched from the same directory. The new version recognized the earlier receipt and read a minimum of 23 frames. An independent silent client requested 23 frames and read 23 both at the start and just before stopping. Version 1.0.0 then restored factory settings. These period observations can be compared with the REAL reading above. Actual game end-to-end latency, audio quality under sustained high load, and behavior on a second physical computer still require separate testing.

## Checking another audio application or sound device

1. **Record a baseline for the same format.** Identify the target active playback endpoint. Record the Windows and driver versions, endpoint direction, shared mix format, and Windows default output format. Activate `IAudioClient3` on that endpoint and use `SetClientProperties` to set the client category, offload, and RAW options explicitly. Pass the same mix format to `GetSharedModeEnginePeriod` and record the default, fundamental step, minimum, and maximum. Use `GetCurrentSharedModeEnginePeriod` to record the frame count and format before opening the stream. [Querying supported shared-mode periods](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-getsharedmodeengineperiod)
2. **Verify the stream that makes the request.** If `Min ≤ N ≤ Max`, the fundamental step is positive, and `N % Fundamental == 0`, request N frames with `InitializeSharedAudioStream`. Record the initialization result, `GetBufferSize`, and the current format and frame count after starting and just before stopping. Verify that the audio clock advances. Other shared clients can affect the engine, so record which clients are active. Keep the observed results even if starting fails, the period differs from the request, or the format changes. When observing only the actual application, at least align its playback start and stop times with the endpoint readings. [Initializing a shared audio stream](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)
3. **Check what the driver provides.** Start with an option the driver officially supports, change one variable, and keep the endpoint, format, and client parameters comparable. Record the driver interface declaration, the range Windows advertises, and the period while the application is running. If switching profiles causes re-enumeration, locate the active endpoint again from the device. The ZH3's named profiles, service names, interface references, OEM property wrapper, and restorable factory properties all require separate confirmation for each vendor.
4. **Keep enough evidence for someone else to repeat the check.** For each setting, retain the four same-format readings before the change, after it, and after restoration. Also keep the requested frame count, observed periods at the start and end, buffer capacity, and run duration. Use consistent anonymous identifiers for the device and endpoint when sharing results. Quantifying any improvement in game responsiveness requires before-and-after end-to-end latency measurements on the same input and audio path. Assessing suitability for daily playback requires long-running audible tests under the intended load, with any dropouts recorded.
